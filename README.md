# JetRover Simulation Workspace

Simulation workspace for the **JetRover** robot (Hiwonder) — a Mecanum chassis
+ 5-DOF arm + gripper, running on **ROS 2 Humble** + **Gazebo Sim (Ignition
Fortress 6.18)** + **MoveIt 2**. URDF/mesh source: the official
[github.com/Hiwonder/JetRover](https://github.com/Hiwonder/JetRover)
(branch `Jetson_Orin_ros2`).

## Layout

```
src/simulations/
├── jetrover_description/   # URDF/xacro + meshes + RViz display
├── jetrover_gazebo/         # World, bridge config, Gazebo integration launch
└── jetrover_moveit_config/  # SRDF, controllers, planning — generated by MoveIt Setup Assistant
```

## Build

```bash
cd ~/ros2_ws
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

## Required environment variables

Every launch below needs the chassis type and LiDAR type declared before
running (read by `jetrover.xacro`/`jetrover_sim.xacro`):

```bash
export MACHINE_TYPE=JetRover_Mecanum   # or JetRover_Tank / JetRover_Acker
export LIDAR_TYPE=A1                   # or G4 / A2 / S2L / LD14P
```

## Action groups for color pick

`color_pick.yaml` uses four derived action groups suffixed `_release`. After
cloning the workspace, create them from the existing
`place_left/center/center1/right.d6a` groups in the library:

```bash
python3 ~/ros2_ws/scripts/provision_color_pick_release_groups.py
```

By default the script reads/writes `~/ActionGroups` (or
`ARM_MOTION_LIBRARY_DIR`), does not overwrite existing `_release` files, and
errors out if a source group is missing. Each `_release` copy keeps the entire
source group intact except that the gripper value of the **final step** is set
to the OPEN detent per the `jetrover_arm.yaml` profile.

Re-teaching workflow: open and teach the source `place_*` group in the arm
editor, save it, then regenerate the derived copies with:

```bash
python3 ~/ros2_ws/scripts/provision_color_pick_release_groups.py --force
```

Do not teach the `_release` group directly. The arm editor may normalize every
gripper value in the source file to a pulse detent (e.g. around `596` for
CLOSED); that is expected. The script does not look for pulse `400`: it only
opens the gripper on the final step, so the workflow above still works after the
editor re-saves the file.

> ⚠️ Only **JetRover_Mecanum** has wheels that actually turn in Gazebo physics
> (`continuous` joints). Tank/Acker still display the correct shape in RViz but
> their wheels are currently `fixed` joints (display only, not yet drivable in
> Gazebo).

## Three run scenarios

### 1. View the 3D model in RViz only (lightest, no physics)

```bash
ros2 launch jetrover_description sim_display.launch.py
```

Uses `robot_state_publisher` + a custom `default_joint_state_publisher` node (in
place of `joint_state_publisher_gui`) + `rviz2`. No Gazebo needed.

### 2. Full Gazebo physics (wheels really roll, LiDAR/IMU/camera produce data)

```bash
ros2 launch jetrover_gazebo gazebo.launch.py
```

Spawns: a world with 2 obstacle boxes, the robot spawned with the
`MecanumDrive` + `OdometryPublisher` + `JointStatePublisher` plugins and the
`gpu_lidar`/`imu`/`rgbd_camera` sensors. Main ROS 2 topics:

| Topic | Direction | Notes |
|---|---|---|
| `/cmd_vel` | ROS→Gazebo | `geometry_msgs/Twist` |
| `/odom`, `/tf` | Gazebo→ROS | odom→base_footprint |
| `/scan` | Gazebo→ROS | LiDAR |
| `/imu` | Gazebo→ROS | |
| `/depth_cam/image`, `/depth_cam/depth_image`, `/depth_cam/camera_info` | Gazebo→ROS | depth camera |
| `/joint_states` | Gazebo→ROS | all non-fixed joints |

Quick drive test:
```bash
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.3}}"
```

### 3. Gazebo + MoveIt (obstacle-aware arm motion planning)

```bash
ros2 launch jetrover_gazebo gazebo_moveit.launch.py
```

Includes everything from scenario 2, plus:
- `gz_ros2_control` hosts `controller_manager` inside the Gazebo process,
  driving the 5 arm joints (`joint1..joint5`) + gripper (`r_joint`) via
  `arm_controller`/`gripper_controller` (`JointTrajectoryController`).
- `move_group` + the RViz **MotionPlanning** panel — drag a goal, click
  **Plan & Execute**, and the arm plans a trajectory that avoids the 2 world
  obstacle boxes and self-collision, using an Octomap built from the depth
  camera (`/depth_cam/depth_image`).
- The NVIDIA GPU is forced for Gazebo rendering (see the GPU section below).

Change chassis: `export MACHINE_TYPE=JetRover_Tank` (etc.) before launching —
note that physical driving only works with Mecanum, as noted above.

## GPU

The machine uses hybrid graphics (Intel iGPU + discrete NVIDIA, PRIME
on-demand mode). Both Gazebo launches (`gazebo.launch.py`,
`gazebo_moveit.launch.py`) already set `__NV_PRIME_RENDER_OFFLOAD=1` +
`__GLX_VENDOR_LIBRARY_NAME=nvidia` to force rendering (Gazebo GUI, depth camera,
`gpu_lidar` LiDAR) onto the discrete GPU instead of the Intel iGPU. Check that
the right GPU is in use:

```bash
nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv
```

**Octomap (MoveIt) and costmap (Nav2) always run on the CPU** — this is the
standard ROS 2/MoveIt architecture; there is no official GPU build for these in
Humble. Only the *generation* of sensor data (LiDAR raycasting, camera image
rendering) can be offloaded to the GPU.

## Issues encountered & fixes (reference when making further changes)

| Problem | Cause | Fixed in |
|---|---|---|
| Meshes not showing in Gazebo | `package://` rewritten to `model://`, missing `GZ_SIM_RESOURCE_PATH` | `gazebo.launch.py`, `gazebo_moveit.launch.py` |
| Wheels spin but the robot doesn't move | Wheel joints were `fixed` (display only) | `jetrover_description/urdf/car_mecanum.gazebo.urdf.xacro` (copy switched to `continuous`) |
| Arm "sags" under gravity | Missing `position_proportional_gain` for `gz_ros2_control` | `jetrover_moveit_config/config/jetrover.ros2_control.xacro` |
| Gripper fingers "break"/wobble | Gazebo Fortress (6.18) doesn't support physics for the `<mimic>` tag | Added `<dynamics damping friction>` to the 5 mimic joints, `jetrover_description/urdf/gripper.urdf.xacro` |
| `move_group` crashes on startup | `max_velocity`/`max_acceleration` were integers instead of floats in YAML | `jetrover_moveit_config/config/joint_limits.yaml` |
| Octomap not receiving camera data | The camera's Gazebo TF frame (`jetrover/link4/depth_camera`) differs from the URDF link name (`depth_cam_frame`) | Static TF bridge in `gazebo_moveit.launch.py` |
| Package name contained a stray newline | Typo in the save path from MoveIt Setup Assistant | Scanned & fixed across all of `jetrover_moveit_config` |
